# 项目规范

本规范约束当前 CHI RN/HN/SN 工程的新增和修改工作。项目以 `model/chi_vip` 为演进主线，`esl_sim` 为默认应用入口；协议核心仍需支持独立构建。整理规范不改变已实现的协议行为，也不要求为统一风格批量重命名已有代码。

“必须 / 不得”表示工程约束，“建议”允许按具体问题选择。本文描述约束，专题文档解释实现和操作方法；后续功能规划不是已经完成的能力。

## 2. 目录与依赖边界

| 目录 / 目标 | 职责 | 依赖边界 |
| --- | --- | --- |
| `foundation/`、`kernel/` / `esl` | 时间、配置、日志、生命周期和通用调度 | 不依赖具体 RN/HN/SN；第三方配置和日志库封装在平台内 |
| `model/chi_interface/` / `esl_chi` | 标准 flit、四通道运输、link credit | 仅依赖标准库，不承担事务或一致性决策 |
| `model/chi_vip/rn/`、`hn/`、`sn/` / `esl_chi_vip` | 三类节点的协议与功能状态 | 核心只依赖标准库和 CHI 载荷定义，不依赖端口、ModelBase、日志库或 TOML |
| `model/chi_vip/include/`、`src/` | 共用类型、规则，以及分别编入不同目标的适配代码 | 同目录不表示同一依赖层；以所在构建目标区分核心和适配 |
| `esl_chi_vip_transport` | 核心事件与 CHIPort 互换 | 依赖核心和 `esl_chi`，不依赖平台 |
| `esl_chi_vip_adapter` | RNModel、HNModel、SNModel | 依赖运输层和平台；将节点接入 Work/Xfer |
| `model/chi_vip/system/` / `esl_chi_vip_system` | 拓扑装配、负载、数据参考、结果统计 | 依赖平台适配；应用策略不得反向进入协议核心 |
| `top/` / `esl_sim` | CLI、输入输出文件和进程退出 | 保持薄入口，不实现协议状态机 |
| `config/`、`tests/`、`tools/`、`doc/` | 配置、验证、开发工具和文档 | 测试和工具不得成为仿真程序的运行依赖 |

RN、HN、SN 分别保留 `include/`、`src/` 和 `ARCHITECTURE.md`；公共 API 放 `include/`，内部状态和实现放 `src/`。新增共享代码必须有明确的跨组件用途，不能把单个节点实现搬进公共目录来绕开依赖边界。

公共平台及 CHI 接口使用 `esl` 命名空间，VIP 使用 `esl::chi_vip`，内部辅助代码使用内部命名空间或私有实现。保留现有 CHI 载荷命名特例，不另建同义 flit 或第二套节点实现。新增模型应遵循现有分层，不恢复已移除的最小只读子系统作为默认路径。

构建使用目标级依赖和包含目录；引入源文件时确认它属于核心、运输、平台还是应用目标。协议核心的修改不能使独立 VIP 构建要求 spdlog、toml++ 或 ModelBase。

## 3. 协议与组件职责

当前基线为 CHI G.b 指定事务集合，默认多 RN-F、单 HN-F、单 SN-F，64B 行、256-bit DAT、Normal memory、Non-secure。具体 opcode、缓存状态、合法字段及例外以能力表和规则为准，不能仅凭某个字段或枚举已经定义就宣称支持其流程。

| 组件 | 必须保持的职责 |
| --- | --- |
| RN | 请求与 snoop 独立推进；统一协调缓存变化、同行排队、回填和 CopyBack 竞争；本地 Store 遵循权限并产生可观察记录 |
| HN | 一致性序列化、目录、逐行等待、snoop 汇聚和下游映射；不得假定能观察 RN 静默 UC→UD；当前无 LLC |
| SN | 仅受理角色允许的下游事务，管理写 DBID、组包与异步内存服务；不能直接承担 RN 一致性请求 |
| 运输适配 | 路由 flit、处理各通道背压，分别报告 TX 入队和实际发送；不决定缓存权限 |
| 系统 / 测试驱动 | 提交业务、初始化内存、检查结果和排空；不替节点生成内部协议决策 |

节点之间只能通过运输层交换消息，不得读取对端缓存、目录或事务表，也不得同步调用对端服务取得最终数据。系统和测试可以使用公开诊断接口选择合法维护操作；实际数据迁移和权限变化仍须经过 CHI。内存初始化与最终读取使用管理接口，不能绕过正常事务服务。

SNP 目的节点属于 `SendAction.destination` 等运输元信息，不向 `CHISnpFlit` 添加非标准 TgtID。Link credit 由端口管理，Protocol credit 由事务核心管理，不能互相替代。

新增或修改协议规则必须说明规范章节或表号、适用 opcode / 状态 / 字段、动作及完成条件，并有独立预期的测试；规则编号保持稳定。合法但未启用的功能报告 `kUnsupportedFeature`，线上非法字段或流程报告 `kProtocolViolation`，不得默认成功。用户提交错误、配置错误、生命周期错误按对应错误类型处理。

## 4. 事件、时序与状态可见性

当前采用 C++17、单线程、单时钟、整数 ps 时间和启动复位。内核交付事件，节点核心通过输入事件、就绪队列、资源等待队列及到期队列推进；不得新增“每周期扫描全部 outstanding 以找可执行事务”的常规路径。端口和应用驱动仍可按周期调用，当前不实现空闲跳时。

周期契约如下：

1. **Prepare**：交付到期事件；应用提交新操作、消费上一周期已提交的完成记录。
2. **Work**：各适配器推进端口，交付到达消息和上一周期发送确认；核心执行 `BeginCycle`，输出动作并尝试入队。
3. **Xfer**：必须在所有模型 Work 完成后开始；推进端口实际发送，保留发送 token 和原始周期，核心 `Commit` 发布状态与完成。
4. **下一周期**：向核心交付实际发送确认；跨节点消息最早在下一周期可见。新到 link credit 不得用于到达当周期发送。

内核还保留通用 ProtocolLink 的 Resolve / Publish 钩子；当前 CHI 端口由节点适配器驱动，不单独作为 ProtocolLink 注册。不得同时由两个调度路径推进同一端口。

以下时刻必须分别建模：动作生成、TX 入队、实际发送、对端可见、请求方完成、协议资源回收。`Send()` 成功只能证明本地入队；不能据此释放 TxnID、DBID 或行级资源。适配器必须保留每个输出的唯一 token，背压重试不得产生重复逻辑动作。

核心接口只在其约定阶段调用；Work 内工作状态不能被跨节点观察当作已提交状态。当前事务在 `BeginCycle` 中原位推进，`Commit` 发布缓存 / 目录视图、完成、观察记录及内存写入，并不提供整个核心的推测执行或回滚能力。

Observer 只做被动记录和检查，不得在回调中重入节点推进或提交跨节点业务；需要激励时安排到后续 Prepare。这是调用约束，不代表现有代码已自动阻止所有回调重入。确定性不能依赖指针地址、无序容器遍历、模型注册顺序或日志开关；随机激励必须使用显式种子。节点可采用不同事件优先级，但必须明确且稳定。涉及调度的修改必须比较正反 Work/Xfer 遍历结果。

## 5. 标识、资源与数据完整性

- 逻辑 Handle、线上 TxnID、对端 DBID、发送 token 和代次分别管理。重试保留逻辑历史，旧定时器或发送确认不得命中新事务；下游事务与 snoop 使用独立分配和父子映射。
- 请求至少按发起 NodeID 与 TxnID 关联；写 DAT 和 CompAck 按相应流程的节点、DBID 关联。不同通道不能统一假定使用原请求 TxnID。
- Protocol credit 按授予节点和 PCrdType 记账，支持 PCrdGrant 先于 RetryAck；`AllowRetry=0` 必须有相应受理保证，不得再次 Retry。资源释放唤醒相关等待者，并维持规定顺序与公平性。
- RN 前端容量不足返回背压；HN/SN 按协议重试与已授予资源保证处理容量不足。为 snoop、响应和已承诺完整数据保留进展路径。阻塞同一行的请求不能阻塞响应接收，也不能停止独立 snoop 引擎。
- 64B 数据、有效字节、脏字节和错误标记分别跟踪。部分写只修改 BE 指定字节；重复拍、缺拍、非法 DataID 和错误标识不能被组包过程静默吞掉。
- 最新值可能位于 RN。HN 接收脏责任后，必须确保最新数据仍有可靠承担者，或已写入 SN，才能释放唯一最新副本。不得始终把瞬时 SN 数据当作参考值。
- 诊断超时不是 CHI 固定完成期限，不能靠超时伪造成功、丢弃责任或自动回收仍在协议使用中的标识。

成功结束必须消费完成队列，并排空事务、待交付事件、发送动作、发送确认、链路在途数据和应返回的 credit。Link credit 的可用余额可以处于正常容量值，不要求所有计数都为零。核心 `IsIdle()` 也不意味着缓存行已经失效；需要比较最终 SN 数据时，必须先执行合法写回或清洁，再等待协议排空。

## 6. 配置、诊断与输出

配置在启动阶段解析、校验并冻结，优先级为默认值 → TOML → 显式 CLI。拒绝未知字段、非法类型、越界参数和输出文件冲突，不能默默忽略拼写错误或非法组合。物理时间明确使用 ps，周期参数明确使用 cycles，不隐式混用。

新增用户可配置参数时，同时维护强类型字段、解析、默认值、校验、TOML 序列化、适用的 CLI、正反测试和运行文档。仅供 C++ 接入的参数明确标注，不自动假定存在配置文件映射；当前 CHI 通道参数仅通过 C++ API 设置。

平台日志和协议观察记录不决定事务推进。普通背压不抛异常；合法事务的数据 / 非数据错误经完成记录报告；不可恢复的协议或生命周期错误停止运行并保留诊断。不得捕获异常后伪造完成或继续运行已损坏的上下文。

结果必须说明统计对象、单位和区间。当前 `completed / loads / stores` 统计用户操作，四通道 flit 数包含维护流量，`throughput = completed / cycles` 包含启动和清理排空周期；不得称为稳态吞吐。`last_time_ps` 是最后执行的边沿时间。字段或语义变化需同步更新消费者、测试和文档，并说明兼容影响。

Trace 保留实际发送时刻，不用确认交付周期替代；确定性比较应排除明确属于运行配置差异的字段。异常输出也需保留失败状态，输出写入失败必须报告。结果数量不能代替协议规则覆盖率。

## 7. 测试与变更验收

预期结果不得调用主动模型的事务处理或规则选择函数来计算。可以共用字段类型和编码定义，但协议关联、状态预期和数据参考应独立；错误注入必须证明错误被检测，不能仅断言程序没有崩溃。并发检查尊重合法因果关系，不强行匹配唯一消息排列。

按改动影响选择验证范围；下表是最低范围。相关检查通过且没有新问题后，不为凑检查数量重复运行。所有可执行命令集中在[构建与运行](build_and_run.md)，用例选择以 `ctest -N` 和 CMake 注册为准。

| 改动类型 | 必须完成的验证 |
| --- | --- |
| 纯文档、注释说明 | 核对接口事实、相对链接、示例及交叉引用；未改行为时不要求全量仿真 |
| 纯格式、命名或文件移动 | 格式检查、受影响目标编译；涉及目录 / include / 公共 API 时检查两个构建入口和受影响测试 |
| RN/HN/SN、共用规则或内存后端 | 独立 VIP 严格构建、受影响规则及负向测试、真实三节点系统测试；全工程应用回归确认接入 |
| CHI 端口、适配器、事件、credit 或 Work/Xfer | 接口测试、背压 / 延迟 / 资源生命周期测试、平台连接、反转遍历、压力及全工程回归 |
| foundation、kernel 或应用装配 | 公共平台测试、应用 runner、默认运行、CLI；影响时间或执行顺序时加反转遍历和系统回归 |
| 配置、CLI、默认值或 JSON / Trace | 校验正反例、TOML 往返、CLI 覆盖、输出解析、默认配置运行；有行为影响时加对应系统测试 |
| CMake、工具链或依赖 | 从重新配置开始验证两个受影响构建入口及其测试；依赖版本 / 校验值修改需验证准备流程 |
| 标识回收、容器生命周期、缓冲区、数据组包等内存相关变更 | 在对应功能测试外运行 ASan/UBSan 构建；记录环境选项和未覆盖项 |

协议功能交付必须覆盖合法流程、错误流程、资源压力、数据完整性、确定性和最终排空。新增能力不能仅靠枚举值、占位分支或关闭检查计入完成。性能时序校准与协议功能验收分别报告。

### 已有工具与人工检查的边界

| 检查 | 当前方式 | 不能据此推断 |
| --- | --- | --- |
| C++17 与严格警告 | CMake 设置及 `-Wall -Wextra -Wpedantic -Werror` | 警告通过不等于协议正确 |
| C++ 格式 | 显式运行 `format-check` / `tools/check_format.py`，只读检查 `.h/.hpp/.cpp` | 不检查 Python、Markdown、命名含义或架构依赖；普通 CTest 不会自动执行它 |
| 功能回归 | CTest 注册用例 | 用例数量不等于完整规范覆盖；当前仓库不因此自动具有 CI 门禁 |
| RN 规则表 | ID 唯一、规范引用非空及集合覆盖检查 | 不自动判断引用章节的语义，也不代表 HN/SN 全部规则覆盖 |
| 第三方依赖 | 准备脚本校验下载包 SHA-256，CMake 核对版本 / hash 标记 | CMake 不会重新计算已解压源码的完整 hash |
| 内存安全 | `ESL_SANITIZERS=ON` 的独立构建及实际运行 | 未插桩目标不属于插桩覆盖；WSL 配置关闭 LeakSanitizer 时不能宣称泄漏检查通过 |
| 协议关联和数据检查 | 独立测试驱动 / 总线审计，以及应用字节参考 | 不等同于已有对外完整通用监视器、覆盖率平台或完整 G.b 认证 |
| 架构、规范引用、文档一致性 | 代码与文档审查 | 目前没有自动架构或 Markdown 链接检查目标 |

## 8. 日常开发与交付

开始修改前查看工作区状态和相关实现，保留已有用户修改，不通过恢复旧目录或批量格式化掩盖任务范围。先确认问题属于协议、运输、平台、应用还是文档，在对应层解决；不要为了一个例子引入第二套通用框架。

新增构建产物、运行日志、JSON、Trace、依赖下载和临时规范提取放在明确的构建或输出目录，不作为源代码提交。本地 CHI 规范 PDF 仅供开发参考，不随仓库分发；在本地放到本文链接指向的位置即可。测试输入和有意保留的参考数据应放在测试用途明确的位置。输出目录按 [.gitignore](../.gitignore) 管理，但不能用忽略规则代替检查实际提交内容。

设计文档描述最终实现，标明当前能力和后续规划。接口或流程变化时更新对应 RN/HN/SN 架构说明；参数和命令变化更新运行文档；模块边界变化更新本文及总体架构。具体参数、命令和支持矩阵各自只维护一个主要来源，其他文档引用它。

交付说明应包含：解决的问题、最终行为、受影响入口、实际执行的验证及结果、未运行或被环境限制的检查。失败、超时和未支持功能如实报告，不沿用历史通过数量作为本次证据。无需为日常可逆实现另设审批步骤；公开接口或兼容性调整在变更说明中明确影响。
